## 〇、项目到底是什么?(先建立整体画面)

你想做的是一个**论文问答机器人**:你问它"RAG-Sequence 是什么?",它给你一段答案,并且**必须告诉你这个答案出自哪篇论文、哪个章节**(这叫"可溯源")。

**为什么必须可溯源?** 因为大模型(LLM)有个毛病:**它说话很流利,但会一本正经地胡说八道**(这叫"幻觉" hallucination)。你肯定见过 ChatGPT 编造不存在的引用。所以这个项目的核心不是"答得顺溜",而是"**答得可信**"——每个回答都能指回一篇真实论文的真实章节。

**一句话**:你造的不是聊天机器人,而是一个**"有出处的学术助理"**。

**北极星指标** = **引用正确率(论文+章节两层都对)**。意思是:光论文对不算,章节也得对,才算这个引用正确。

## 一、为什么实验要"这么设计"?——控制变量法

科研最核心的思维是**对比实验**。你的研究问题 RQ1 问的是:

> "Dense(语义检索)、Hybrid(混合)、Hybrid+重排,三种检索方式,对答案质量有什么不同影响?"

要回答这个,你得像做菜一样**只换一个调料,其他全部不变**:
- 切块方式固定(fixed 512)
- 生成模型固定(DeepSeek)
- Top-K 固定(5 个)
- 评估集固定(同一套 50 题)
- **只改:检索方法**

这就是 Day 8~12 在做的事:**把"换调料"拆成一步步,每一步都验证做对了没有**。如果一次全做完,出了结果你根本不知道是哪个环节的问题。

整个设计是一条"**地基往上盖楼**"的顺序:

```
Day 6  处理语料  (12 篇 PDF → 干净的文本)                → 图书馆的"书"
Day 7  切块      (每篇切成 512 token 的段落)            → 书的"页码段落"
Day 8  Dense 检索(给段落建语义索引)                     → 图书馆的"主题索引"
Day 9  接 LLM    (让机器人开口回答并强制标引用)         → 让"图书管理员"开口
Day 10 评估集    (造 50 道题 + 标准答案 + 答案所在段落) → 一张"考试卷"
Day 11-12 跑实验 (用考试卷量三种检索方式)               → 给不同方案"打分"
```

**每一步都必须站在前一步之上**——语料脏、切块乱,后面全错。

## 二、Day 8~12 逐日通俗讲解

统一比喻:**知识库 = 一座图书馆,系统 = 图书管理员**。

### Day 8:Dense Retrieval(给图书馆建"语义索引")

- **干什么**:把 439 个段落都喂给 bge-m3 模型,每个段落变成一个"向量"(一串数字,可理解为段落的"意思指纹")。你问问题,也把问题变成向量,然后找出"意思最像"的段落。
- **为什么要这样**:早期检索(BM25)是"**按词找**"——搜"villain"(反派)找不到写"bad guy"(坏人)的段落,因为词不一样。Dense 是"**按意思找**"——"bad guy"和"villain"意思一样,向量接近,就能找到。
- **比喻**:BM25 像图书馆的"关键词卡片"(只有标题里出现的词能查到),Dense 像"主题目录"(按内容大意归类)。
- **关键代码**:`src/retrieval/dense.py` 的 `DenseRetriever`。它把"编码(变成向量)"和"检索(找最像的)"封装起来,`search(question, top_k)` 返回命中的段落列表。

### Day 9:接 LLM 并强制"标引用"(让管理员开口,且必须报出处)

- **干什么**:把检索到的 top-5 段落拼成"上下文",喂给 DeepSeek 回答。**关键**是提示词硬性规定:只能依据给定段落回答、没证据就拒答、引用必须用 `[1][2]` 标注,程序再把编号**映射回真实的 Chunk ID**。
- **为什么这么设计(全项目的灵魂)**:你没让模型自己报"章节号",而是让模型报编号、程序查编号对应的真实段落。**让模型猜章节 = 测它的运气,不是测检索能力**。你的实验想测"检索器有没有把正确答案捞出来",所以章节信息必须由检索器带回,模型只负责选。
- **比喻**:图书管理员只能引用你递给他那几本书里的内容(检索结果),不能凭记忆瞎编书名。他引用时只需说"这段来自第 2 本",你去查第 2 本是谁——这样他没法撒谎。
- **关键代码**:`src/generation/prompts.py`(提示词模板)、`src/generation/generator.py`(调用 LLM + 解析引用编号)、`src/pipeline.py`(把检索+生成串起来)。

### Day 10:造评估集(出考题)

- **干什么**:人工确认了 50 道题,分 5 类(事实题 15、方法理解 10、对比题 10、跨章节 5、无答案 10)。每道题都有:标准答案、答案所在论文、答案所在段落(relevant chunks)、以及"能不能答"(answerable)。
- **为什么这么设计**:要"打分",先有"标准答案"。而且分类很重要——
  - **无答案题**(10 道)专门考"拒答":系统拒答 = **正确**(真拒答);知识库有答案但系统没答出 = **错误**(误拒答)。
  - 对比题/跨章节题考"整合多篇/多章节的能力"。
- **关键代码**:`data/evaluation/questions.jsonl`(定稿数据)、`scripts/build_questions.py`(落盘+校验)。

### Day 11:E1 实验(第一次用考试卷量 Dense)

- **干什么**:50 题全跑一遍,算分。还做了"**神谕检索**"(oracle)——不跑检索器,直接把标准答案所在的段落喂给模型。这是**归因工具**。
- **为什么要有 oracle**:引用正确率只有 60% 时,你不知道是"检索器没找到对的段落"还是"模型答得差"。oracle 帮你分离:
  - 真实 60%,oracle 90% → **差距是检索的锅**(检索器没捞到对的)
  - oracle 也只有 60% → **不是检索的问题**,是生成器或评估集标注的问题
- **实际发现(你自己趟出来的科研!)**:oracle 有 32.5% 误拒答 → 一查发现评估集有问题(对比题只标了一篇论文的段落)。修正后降到 17.5%。**实验设计帮你精准定位"锅在谁头上"。**
- **关键代码**:`scripts/run_experiment.py`、`src/evaluation/retrieval_metrics.py`(Hit@K/MRR)、`src/evaluation/generation_metrics.py`(引用正确率/拒答判定)。

### Day 12:E2/E3 对比实验(BM25 和 Hybrid)

- **干什么**:实现了 BM25(关键词检索)和 Hybrid(语义+关键词用 RRF 融合),各跑一遍,和 Dense 对比。
- **实际结果**:
  - BM25 惨败(Hit@1=0)——题大多是中文语义题,按词找根本捞不到
  - Hybrid 略输 Dense——但逐题看,E1 里 11 个检索失败的题,Hybrid 找回了 10 个!
- **这个"负结果 + 意外发现"就是真实科研**:BM25 不好用不是失败,是**可发表的结论**;Hybrid"召回增强、排序略损"是 RQ1 的细致答案。
- **关键代码**:`src/retrieval/bm25.py`、`src/retrieval/fusion.py`(RRF 融合)。

## 四、小白怎么打通这个流程?(实操路径)

流程就是"照抄每一步,每步验证":

1. **别跳步**:语料脏就后面全错 → 先 `build_documents` → `build_chunks`,每步用测试固化(你已有 76 项测试)。
2. **检索器统一接口**:Dense/BM25/Hybrid 都用同一个 `search(question, top_k) -> 命中列表` 函数——**最关键的抽象**,跑实验时换检索器像换电池,实验代码一行不改。
3. **评估集先建后跑**:先造 50 题(人工确认),再跑实验。**永远先造尺子,再量东西**。
4. **每跑一组实验先提交 git**:config 记录 commit hash → 结果才能追溯。
5. **跑完必看 oracle**:别只看总分,用 oracle 归因"是检索的锅还是生成的锅"。

## 五、设计遇到的真实困难(都是你走过的坑)

1. **PDF 提取丢数字**(Day 6 埋雷,Day 11 爆):DPR 论文摘要页的"65.2%"被 pypdf 弄丢,导致评估题标准答案在知识库检索不到 → 系统拒答。**对策**:把题改成知识库里有依据的(Table 2 的 k∈{20,100})。
2. **评估集相关段落只标单篇**:对比题"RAG vs FiD"只标了 RAG 的段落,oracle 喂进去没有 FiD 内容,模型答不了。**对策**:神谕消融揪出来,补上另一篇的 chunk。
3. **"章节对"怎么算**:参考答案写"5 Experiments",chunk 实际是"5.2 Ablation Study",直接比对对不上。**对策**:用"章节号前缀匹配"(5 和 5.2 算同一章)。
4. **BM25 对中文完全失效**:词面匹配在语义题上崩掉。**对策**:如实记为负结果,同时发现它能补 Dense 盲区(英文/数字 token 命中)。
5. **Windows 编码坑**:控制台 GBK 打印不了论文里的数学符号 → 强制 UTF-8。
6. **可追溯性**:实验代码改一行没提交,config 记的 commit 就不准 → 先 commit 再跑实验。

这些坑每一个都是自己趟出来的,写进报告就是"经验与教训"。

## 六、最关键:怎么从论文里找解决方案?

**整个项目最"学术"的地方——每一步设计都能在 12 篇论文里找到依据。** 遇到问题先问"有没有论文讲过这个":

| 遇到的困难 | 翻哪篇论文 | 论文给的答案 |
|---|---|---|
| 用语义还是关键词检索? | **DPR** | DPR 证明 dense 比 BM25 强 9-19%,但也警告"小语料未必迁移"→ 所以亲自测 |
| 模型爱编造怎么办? | **RAG** + **RGB** | RAG 给检索+生成框架;RGB 教"负向拒答"(没证据就拒绝)|
| 引用对错怎么判? | **Verifiability** | 它提出"引用召回+引用精度"两层标准——你的"论文+章节双层"是它的细化 |
| 没答案该不该答? | **CRAG** + **RGB** | CRAG 教检索失败要纠错;RGB 教测拒答能力 |
| 检索越多越好吗? | **Lost in the Middle** | U 型曲线:喂太多、放中间反而更差 → 做 Top-K/重排实验的动机 |
| FiD 说越大越好、LitM 说越大越差? | **FiD** + **LitM** | 两篇矛盾 → 正是 RQ3 要实测的问题 |
| 评估指标怎么选? | **Ragas** + **RAG Survey** | Ragas 给免标注 faithfulness;Survey 给"质量分+四能力"框架 |
| 怎么系统拆解问题? | **CRUD-RAG** | 教"组件消融"——逐块拆开看哪个环节影响大(你做的 oracle 就是这思想)|

**核心方法**:读论文不要只看结论,要**带着自己的问题去读**。先有疑惑 → 去论文找依据 → 用实验验证。这就是科研。
